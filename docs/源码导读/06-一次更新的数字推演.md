# 数字推演：一次 650 步的运行到底发生了什么

> 前五篇讲“每个零件怎么工作”，这一篇把它们按时间顺序串起来，全部用真实运行留下的数字。读完后你应该能只看日志和配置，就复述出“第 1 步、第 82 步、第 325 步、第 650 步各做了什么”。

数据来源：`configs/fusion_continue_20261021.json`、`runs/fusion_continue_20261021/*/updates_*.jsonl`、`selected_all.json`、`evaluation/report.json`。

---

## 1. 先把配置换算成常数

| 量 | 计算 | 值 |
| --- | --- | --- |
| 训练行数 N | `data/posttraining/train.jsonl` | 10,398 |
| 查询数 | — | 512 |
| 每 epoch 的更新数 | `ceil(10398 / 32)` | **325** |
| 每 epoch 的批构成 | `324 × 32 + 1 × 30` | 10,398 |
| 总更新数 | `max_updates` | 650（正好 2 epoch） |
| 评测点 | `eval_steps` | 0、82、163、244、325、407、488、569、650（9 个） |
| 学习率端点 | warmup 33 → 2e-5，cosine → 2e-6 | — |
| micro / effective batch | 配置 | 4 / 32 |
| 梯度裁剪上限 | `max_grad_norm` | 1.0 |

两个派生公式，后文反复用：

```
epoch(step)     = step // 325              # step 是循环计数器（已完成的更新数）
batch_no(step)  = step % 325
exposures(s)    = 32·s − 2·⌊s / 325⌋      # 完成第 s 次更新后累计喂入的样本数
```

第一、二行的 `step` 是**循环计数器**，第三行的 `s` 是**第几次更新**（也是日志里写的 `step`），两者差 1。`exposures` 里的 `−2` 来自每个 epoch 的尾批少 2 条（30 而不是 32）。

| 更新编号（日志 `step`） | 完成该更新后的 exposures |
| ---: | ---: |
| 1 | 32 |
| 82 | 2,624 |
| 324 | 10,368 |
| 325 | 10,398（第 1 个 epoch 结束） |
| 407 | 13,022 |
| 488 | 15,614 |
| 569 | 18,206 |
| 650 | 20,796（第 2 个 epoch 结束） |

`selected_all.json` 里 FUSION_KD 选中 488 步时的 `selected_exposures` 正是 **15,614**，CE_CONT/REF_KD 的 569 步是 **18,206**——和公式一致。

## 2. 第 0 步之前：三道门

`train()` 在创建任何训练文件之前先过三关：

1. `gpu_required()`：CUDA + BF16，没有就退出。
2. `audit(cfg)`：核对 10 个文件哈希、10,398 行、512 查询、路由 5,199、融合 5,195、隔离全零、批/预算/评测步契约、两个 epoch 排列（[03 §8](03-fusion-targets.md)）。
3. `identity(cfg)`：新代码的 12 个文件的哈希（[04 §4](04-training.md)）。

然后把 `config`、`identity`、`runtime`、`counts`、`epoch_order_sha256` 写进 `run_manifest.json`。

`epoch_order_sha256` 的两个值来自对 epoch 0/1 排列做 SHA256：

```
d05f2e6af6a6cc1cc017f3bf7983edaccf3250e74eb707b01792257c56234dc6
90bf24cc3a06341558ff1ab15630dc5be770123d1792bb2eaed778dc7bfc2de6
```

它们同时出现在 `run_manifest.json`、每个 `step-XXXX/state.json` 和预检输出里。只要排列变了（种子、行数、代码任何一处），这三个地方都会对不上。

## 3. 第 0 步：未训练的基线

`train_arm()` 发现没有存档，于是：

```python
history = [evaluate_point(model,data['tune'],cfg,0,0,arm_dir)]
snapshot(model,optimizer,arm_dir / 'step-0000', dict(step=0, exposures=0, ...))
```

- `evaluate_point()` 在 tune（5,223 条、256 查询）上推理，写 `tune_step_0000.jsonl`，得到 `point`。
- 三组的第 0 步 Macro-F1 都是 **0.4744**、nDCG@10 都是 **0.7440**——完全一致，因为它们是同一个 S adapter、同一套推理参数。
- `step-0000/` 目录被保存，包括优化器状态与 RNG。这样“选中第 0 步”在物理上也是可行的（如果训练让成绩变差，选点规则会真的选它）。

## 4. 第 1 次更新（计数器 0）：一次更新的完整解剖

### 4.1 取索引（第 383–386 行）

```python
epoch, batch_no = divmod(0, 325)      # → (0, 0)
order = epoch_order(10398, 20261001, 0)
indices = order[0:32]
```

实测 `order0[:8] = [6605, 10396, 4725, 5679, 4631, 1811, 8347, 7557]`，所以第一小批的 4 条是 `6605, 10396, 4725, 5679`。这 32 条的标签分布是 E 17、S 9、I 4、C 2——和训练集的整体比例（E 4,833 / S 3,368 / I 1,681 / C 516）接近，说明洗牌正常。

以第一条 `idx = 6605` 为例：

- 训练行 `label = 'C'`，所以 `labels[6605] = 2`（E=0、S=1、C=2、I=3）。
- 目标 `fusion_probabilities = {E: 0.1532, S: 0.0172, C: 0.7820, I: 0.0476}`，`route_selected = True`、`teacher_used = True`（它在低置信度一半里，且教师有概率）。
- 转成张量的一行是 `[0.1532, 0.0172, 0.7820, 0.0476]`。

对 FUSION_KD 组，这一行的 KL 目标是 `q`；对 REF_KD 组，同一位置会换成 `p_S`；CE_CONT 组取 `p_S` 但只用于记录。**三组用的是同一批索引、同一批编码结果，只有 `targets` 张量的取值不同。**

### 4.2 编码与组批（第 393–395 行）

- 训练开始时已经用 `encode()` 把 10,398 条全部编码好，存在 `features` 列表里；这一步只是按索引取。
- 每条 `features[i] = {'input_ids': [L_i], 'attention_mask': [1]*L_i}`，L 因样本而异（F 上的实测范围是 131–245）。
- 第一小批 `collate` 后：`input_ids [4, Lmax]`、`attention_mask [4, Lmax]`，Lmax 是这 4 条里最长的。

### 4.3 前向（第 396 行）

`model(batch)` → `[4, 4]` logits（[02 §3](02-modeling.md)）。底座 bf16，取末位隐藏表示转 fp32，再与四个标签 token 的权重相乘。

### 4.4 损失（第 397 行）

以 FUSION_KD 为例：`loss_rows(logits, labels[selected], targets[selected], 'FUSION_KD', 1.0)`

- `logp = log_softmax(logits)` → `[4, 4]`
- `ce = −logp[i, labels[i]]` → `[4]`
- `kl = Σ_c q[i,c]·(log q[i,c] − logp[i,c])` → `[4]`
- `loss = (ce + kl) / 2` → `[4]`

### 4.5 反向与累积（第 399 行）

8 个 micro-batch 依次 `(loss.sum() / 32).backward()`。梯度在 `.grad` 里累加，等价于“32 条一起算平均损失再反向”。

### 4.6 裁剪与更新（第 402–404 行）

`clip_grad_norm_(..., 1.0)` 得到裁剪前范数，然后 `optimizer.step()`。`step` 变 1，`exposures` 变 32。

### 4.7 真实日志第 1 行（CE_CONT）

```json
{"step": 1, "epoch": 0, "rows": 32, "exposures": 32, "lr": 6.060606060606061e-07,
 "loss": 0.9640569090843201, "ce": 0.9640569090843201, "kl": 0.00059486847021617,
 "soft_coefficient": 0, "grad_norm_before_clip": 5.341045379638672,
 "clip_applied": true, "seconds_since_process_start": 2.9206760349916294}
```

逐项对照：

| 字段 | 值 | 解释 |
| --- | --- | --- |
| `lr` | 6.0606e-7 | `lr_at(1) = 2e-5 × 1/33` |
| `loss` = `ce` | 0.9641 | CE_CONT 的损失只有 CE |
| `kl` | 0.000595 | 算出来但没进损失（`soft_coefficient=0`） |
| `grad_norm_before_clip` | 5.34 | 裁剪前；大于 1.0 |
| `clip_applied` | true | 因 5.34 > 1.0 |
| `seconds_since_process_start` | 2.92 | 含加载模型、编码 10,398 条、基线评测 |

第 1 步就花 2.9 秒，后面每步约 3.5 秒（2263 秒 / 650 步），因为每步要做 8 次前向 + 反向 + 一次优化器更新。这个速度与模型大小、序列长度、无梯度检查点相符。

## 5. 评测点 `step=82`：第一次中途检查

- 第 82 次更新用的是计数器 81：`divmod(81, 325) = (0, 81)`，仍在 epoch 0。
- 完成该更新后 `exposures = 2,624`，`epoch = 2624/10398 ≈ 0.2524`。
- `step in eval_steps` 成立，于是：
  1. `evaluate_point()` 在 tune 上推理 5,223 条，写 `tune_step_0082.jsonl`；
  2. `history` 追加一个点（CE_CONT 的 Macro-F1 = 0.4635）；
  3. `stop_state(history)` 计算早停状态；
  4. `snapshot()` 写 `step-0082/`（adapter、tokenizer、优化器、RNG、history）；
  5. 打印 `TUNE CE_CONT {...}`。

从这一步开始，`step-XXXX/state.json` 里的 `history` 会越来越长；`selected.json` 最终保存的也是这份 history。

## 6. 计数器 324 与 325：尾批与换轮

先记住一条：训练循环里的 `step` 是“**已完成的更新数**”，第 s 次更新用的是 `divmod(s−1, 325)`。日志里的 `step` 是自增之后的值，所以要把日志的 `step` 往回拨 1，才是“第几次更新”。

### 6.1 计数器 324：epoch 0 尾批（第 325 次更新）

`divmod(324, 325) = (0, 324)`，`indices = order0[10368:10400]`，实际只有 **30** 条（10,398 − 10,368）。

内层按 4 条切：7 块 4 条 + 1 块 2 条。**每个 micro-batch 的分母都是 30**，所以 7×(4/30) + 1×(2/30) = 1，梯度正好是“30 条的平均”。

这一轮更新完成后，日志记为 `step: 325, rows: 30, exposures: 10398`。因为 325 在 `eval_steps` 里，紧接着评测并写 `step-0325/`。此时模型“完整见过一轮数据，但还没开始第二轮”。

### 6.2 计数器 325：epoch 1 第一批（第 326 次更新）

**下一次**进入循环时 `step = 325`，这时才换轮：

```text
divmod(325, 325) = (1, 0)      # epoch 1, batch 0
```

- `epoch` 变成 1，`epoch_order(10398, seed, 1)` **重新洗牌**；
- `indices = order1[0:32]`；
- 日志记为 `step: 326`，`exposures` 从 10,398 变成 10,430；
- 326 不在 `eval_steps` 里，不评测。

> 容易把两件事混在一起：**第 325 次更新**用的是 epoch 0 的尾批，**计数器 325**（第 326 次更新）才开启 epoch 1。差一位是自增时机造成的。

## 7. 评测点 488、569、650：选点与收尾

| 评测点（日志 `step`） | 产生它的计数器 | 本批行数 | exposures | 事件 |
| ---: | ---: | ---: | ---: | --- |
| 407 | 406 | 32 | 13,022 | epoch 1 的常规评测 |
| 488 | 487 | 32 | 15,614 | FUSION_KD 的本次 Macro-F1 = 0.5006，成为该组最高 |
| 569 | 568 | 32 | 18,206 | CE_CONT / REF_KD 的 0.4916 / 0.4968 成为各组最高 |
| 650 | 649 | 30 | 20,796 | 最后一次更新（尾批），随后评测 |

### 7.1 第 650 次更新后评测，然后结束循环

循环条件是 `while step < 650`。第 650 次更新发生在“进入循环时 `step=649`”的那一轮：它训练 `divmod(649,325) = (1,324)` 的尾批，然后 `step` 变成 650，正好命中 `eval_steps`，于是评测、存档、算早停。接着 `while 650 < 650` 为假，循环结束。

所以：

- 存在 **650 行更新日志**；
- 存在 **9 个评测点**（0 在循环外，82…650 在循环内）；
- 第 650 步的存档是“训练结束时的模型”，但不一定是选中的模型。

如果循环继续，第 651 次更新会映射到 `divmod(650,325) = (2,0)`，进入第 3 个 epoch——但配置只允许 2 个 epoch，650 正好卡在边界。

### 7.2 选点复算

`max(history, key=best_key)` 的结果（真实数据）：

| 组 | 选中步 | 选中时 exposures | tune Macro-F1 | tune nDCG@10 | 停止步 | 停止原因 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| CE_CONT | 569 | 18,206 | 0.4916 | 0.7404 | 650 | budget_exhausted |
| REF_KD | 569 | 18,206 | 0.4968 | 0.7474 | 650 | budget_exhausted |
| FUSION_KD | 488 | 15,614 | 0.5006 | 0.7523 | 650 | budget_exhausted |

三组都没有触发早停（[03 §7.3](03-fusion-targets.md) 有逐点计算）。FUSION_KD 的峰值出现在 488 步，之后 569（0.4939）和 650（0.4953）都没有超过它——这是典型的“选点早于停止”。

## 9. 评测阶段：12 次推理 + 2 个参考

`final_evaluation()` 的顺序是 `('S',) + ARMS` × `('tune','gate','F')`：

| 模型 | tune（5,223） | gate（10,438） | F（10,459） |
| --- | --- | --- | --- |
| S | ✓ | ✓ | ✓（另算 S_C50、T 参考） |
| CE_CONT | ✓ | ✓ | ✓ |
| REF_KD | ✓ | ✓ | ✓ |
| FUSION_KD | ✓ | ✓ | ✓ |

- 12 次推理，每次都在**当前环境、当前 batch=8** 下重新算，不引用历史数字。
- S 在 F 上额外产出两个参考系统：`S_C50_reference`（S 预测 + 教师缓存的半量融合）与 `T_cached_reference`（教师原始缓存）。
- 每个模型每个划分写一个 `.jsonl` 和一个 `.meta.json`。文件大小：tune 约 2.4 MB、gate 约 4.9 MB、F 约 4.9 MB。
- 若同名文件与 meta 全部匹配（含 `selected_all_sha256`、adapter 哈希），直接复用；否则重新推理并覆盖。
- 最后算 9 组按查询配对的 Bootstrap（10,000 次），写 `report.json` 与 `RESULT.md`。

F 上的最终成绩（[report.json](../../results/fusion_continue_20261021/report.json)）：

| 系统 | Accuracy | Macro-F1 | nDCG@10 | NLL |
| --- | ---: | ---: | ---: | ---: |
| S | 54.83% | 47.50% | 0.7682 | 1.0423 |
| CE_CONT | 55.88% | 48.31% | 0.7658 | 1.0140 |
| REF_KD | 55.65% | 48.18% | 0.7671 | 0.9974 |
| FUSION_KD | 55.73% | 49.22% | 0.7698 | 0.9914 |
| S_C50_reference | 57.15% | 52.08% | 0.7804 | 1.0181 |
| T_cached_reference | 53.23% | 50.15% | 0.8038 | 1.4052 |

一个值得注意的对照：FUSION_KD 的 Macro-F1（49.22%）**低于** S_C50 参考（52.08%）。也就是说，在线融合的“上限参照”比蒸馏出来的独立学生更高——本轮结果说明的是“蒸馏把一部分收益迁移给独立学生”，而不是“学生追平了融合系统”。报告里的 `limitations` 正是在提醒这类边界。

## 10. 用一条命令复算本文数字

只用标准库，不需要 GPU：

```powershell
python -c "import json,sys; sys.path.insert(0,'src'); from fusion import epoch_order, lr_at; cfg=json.load(open('configs/fusion_continue_20261021.json',encoding='utf-8')); n=10398; print('order0[:8]', epoch_order(n,cfg['seed'],0)[:8]); print('exposures', {s: 32*s-2*(s//325) for s in (1,82,324,325,407,488,569,650)}); print('lr', {s: round(lr_at(s,cfg),9) for s in (1,33,82,325,488,650)})"
```

```

exposures {1: 32, 82: 2624, 324: 10368, 325: 10398, 407: 13022, 488: 15614, 569: 18206, 650: 20796}

```

```powershell

python -c "import glob,json; p=sorted(glob.glob('runs/fusion_continue_20261021/*/updates_*.jsonl'))[0]; last=[json.loads(x) for x in open(p,encoding='utf-8')][-1]; print(last['step'], last['rows'], last['exposures'])"
```

## 11. 一句话总结整条链路

配置给出 32 条一批、650 次更新 → `epoch_order` 决定每轮顺序、尾批 30 条 → `encode`/`collate` 把 4 条拼成张量 → `forward` 用四个标签 token 的权重得到 `[4,4]` logits → `loss_rows` 按组选 `p_S` 或 `q` 算 `(ce+kl)/2` → 除以 32（或 30）反向累积 → 裁剪、`AdamW.step()`、写日志 → 每 81/82 步评测并整目录存档 → 三组按 Macro-F1→nDCG→更早步选点、冻结 → 12 次推理 + 2 个参考 + 9 组 Bootstrap → `report.json`。
